# Decisions

Status: **final**, agreed by Dr Atul Tiwari on 25 Sep 2026. D-021 to D-027 were added the same day, also agreed, when the project was renamed Sambhasha and joined the Clinical-Case-Sim umbrella. Change a decision only with his explicit approval, and record the change here as a new entry that supersedes the old one. Decisions shared with the Case Library and Nidana live in `../../docs/DECISIONS.md` (S-numbers).

| Id | Decision | Why |
| --- | --- | --- |
| D-001 | Build a **code-driven engine**. The Scheduler, not a language model, decides who acts next. | Reproducible runs; strict information barriers; no chat loops. |
| D-002 | **Hermes Agent is out of scope** for the build. Allowed later only for operations (launching batches, digests), a Discord "theatre mode" that displays runs, and as a contestant playing a seat through an MCP server. | Hermes profiles do not sandbox each other, rooms cap at 6 bots and 3 rounds, and it keeps memory between runs. |
| D-003 | Replace the single "Judge" with four roles: **Case Curator**, **Gatekeeper**, **Synthetic Findings Service** and **Evaluator**. | One agent that knows the answer, talks to the team and grades is the biggest source of leakage and bias. |
| D-004 | The information barrier lives **in data and code**. No seat has file, database, web or code-execution tools. | A prompt can be argued with; a missing table row cannot. |
| D-005 | The Gatekeeper **selects stored text** and never writes its own. A model only maps a request to candidate fact ids. | Prevents leakage by paraphrase and "just tell me the diagnosis" tricks. |
| D-006 | One shared **Chart**. Everything released is visible to every seat on the case; each seat's view is a projection of released events. | Matches a real hospital record; no duplicate requests; measurable behaviour. |
| D-007 | The **Attending Physician** alone orders tests, refers and commits. Consultants examine within their domain and recommend in consult notes. | One accountable decision-maker; referral quality becomes scoreable. |
| D-008 | **Diagnostic Services** act only on orders. They receive sealed raw material plus the requisition's clinical details, write the report, and may suggest reflex tests. Numeric laboratory results are posted directly by the Gatekeeper. | Interpretation is the skill being tested; numbers need no interpreter. |
| D-009 | **One missing-fact rule:** the likeliest result for this patient, given the true diagnosis and the day. Relevance affects only the score. Never answer "not available". Cache by (case, code, day). Never flag a result as synthetic during play. | "Irrelevant" cannot be decided safely mid-case, and "not available" is itself a hint. |
| D-010 | The Synthetic Findings Service uses a **different model family** from the doctor seats, grounds itself in reference ranges, and is checked for consistency and leaks. The Case Reviewer reviews generated values for study cases. | Avoids a model flattering its own mental picture of the disease. |
| D-011 | Case files are **atomic facts** tagged with day, source locator and raw-or-interpretation, with the diagnosis redacted from seat-facing text. Each is human-verified, then frozen and hashed. A change means a new version. | Titles and legends leak diagnoses; frozen files make runs comparable. |
| D-012 | **Licences:** CC0 and CC BY cases may be released and used in the game. CC BY-NC cases are research-only. ND-licensed or unlicensed cases are excluded. **Superseded by D-025 and S-006.** | ND forbids sharing adapted material; NC forbids a paid game. |
| D-013 | **Limits:** a budget in INR (price table based on CGHS rates), a simulated clock (turnaround table), a turn limit and an explicit commit action. | Without limits agents order everything; cost and time are core metrics. |
| D-014 | **Evaluation:** SDBench-style 5-point diagnosis rubric (4 or more is correct), plan scoring through case-specific must-do and must-not-do lists, process metrics, and synthetic dependence. Calibrate the LLM Evaluator against clinicians. | Scores the path as well as the answer. |
| D-015 | **Every seat can be an LLM or a human** with an identical view. Every run starts clean and is written to an append-only Event Log. | Enables human-versus-AI studies. (The teaching game is now Nidana, D-027.) |
| D-016 | **Stack:** Python 3.12 with uv, Pydantic v2, Typer CLI, FastAPI (Phase 3), Postgres through Supabase (local CLI in development, self-hosted in production), psycopg 3, and one OpenAI-compatible client for OpenRouter (cloud) and Ollama (local). Inspect AI arrives in Phase 2; Next.js in Phase 3. (FastAPI and Next.js were for the teaching game, which D-027 moves to Nidana.) | Matches Atul's existing stack and keeps dependencies few. |
| D-017 | **Names** follow the glossary in `docs/SPEC.md` §1 exactly, in code, prompts, logs and documents. | One vocabulary for the team, the paper and the game. |
| D-018 | **Pilot case:** `PMC12949993`, lead poisoning disguised as autoimmune haemolytic anaemia (Cureus 2026, CC BY 4.0). Four more starter cases are listed in `../../case-library/cases/PMC12949993/PILOT_CASE.md` (moved to the Case Library). | Pathology-pivotal, hidden history, fair anchoring trap, several consultants, rich dated data. |
| D-019 | **Pilot seats:** Attending Physician, Challenger, Consultants in gastroenterology, haematology, neurology and clinical toxicology, and the Pathology and Radiology Services. | Covers the pilot's likely referrals. |
| D-020 | **Model choice is configuration**, not code. Doctor seats, the Synthetic Findings Service and the Evaluator are set in `configs/models.yaml`; tests use a scripted fake model and never call a paid API. | Swap models per study without code changes; free, deterministic tests. |
| D-021 | **Cases come from the shared Case Library.** Claude curates each case once in the Case Vault through the Supabase MCP, under the `case-curate` skill, with Atul as Case Reviewer; Sambhasha imports frozen bundles (schema 0.3). Tasks P0.4 (fetcher), P0.7 (Case Curator), P0.8 (review and freeze), P0.9 (pilot verification) and P0.10 (starter set) move to the Case Library; P0.5 (leak scanner) stays as an import-time check; P0.6 imports bundles. Amends D-011 and SPEC §9. | One curation and one review per case, shared with Nidana (S-002). |
| D-022 | **The Gatekeeper's matcher maps each request to shared catalogue ids** and chooses only among them. Release conditions are lists of catalogue ids. Before scoring, the matcher also maps the Commit's diagnosis and plan, and each Diagnostic Service report, to catalogue ids (`DX`, `RX`, `ACT`, `REF`, `FND`) and logs the mapping, so the shared conditions work as in Nidana. Prices and turnaround times come from the catalogue export (`prices_inr.yaml` and `turnaround.yaml` are generated from it). Extends D-005 and D-013. | One vocabulary for requests and scores in both projects. |
| D-023 | **Results for every catalogue item are pre-generated and reviewed** in the Case Library. The runtime Synthetic Findings Service remains only for requests outside the catalogue, and each such request is exported to the Case Library as a missing request. Runs that used it are flagged and kept out of primary results until those items are reviewed and added. Amends D-009. | Reviewed values for everything a seat is likely to ask; the catalogue grows from real requests. |
| D-024 | **Pre-generated values come from Claude.** Runs whose doctor seats are Claude-family models must report this, and the study includes a sensitivity analysis with `affected` values regenerated by another model family. Qualifies D-010. | Keeps D-010's intent: a model should not be graded on values from its own family without a check. |
| D-025 | **Licences (supersedes D-012):** every curated case may be used for development and internal runs, including CC BY-NC and ND cases. Study case sets use only cases whose licence allows public release (`public_release_ok`: CC0, CC BY, CC BY-SA, CC BY-NC, CC BY-NC-SA), so the benchmark can be released; ND cases are for development only. See S-006. | Atul's instruction for development, and a benchmark others can reproduce. |
| D-026 | **The project is named Sambhasha** (formerly the Virtual Diagnostic Team, VDT); code id and CLI `sambhasha`, package `src/sambhasha/`. The glossary of roles is unchanged. | *Sambhāṣā* is the Charaka Saṃhitā's term for structured discussion among physicians (S-003). |
| D-027 | **The teaching game is Nidana**, a separate part of Clinical-Case-Sim that shares the cases. Sambhasha's Phase 3 (teaching game) is superseded; its matcher and Evaluator calibration protocol may be reused by Nidana's voice mode. | Each part does one job; the shared library keeps them comparable. |
| D-028 | **The pilot runs on Google's free Gemini API** (Atul, 27 Sep 2026): every role on Gemini (`configs/models.yaml`), the Attending's second profile on an older Gemini generation. **Exception to D-010** for the pilot only: the Synthetic Findings Service and the Evaluator share the doctor seats' family; the config states the exception and the code refuses a same-family config without one. Free-tier prompts may be used by Google to improve its products; noted, not enforced, because the pilot cases are development-only (S-010). Rate-limit waits are counted per run and reported as the time a paid tier would save. The paid profiles for production and the study are saved in `configs/models.openrouter.yaml`. | No budget for a paid API yet; the pilot cases are public and development-only, and synthetic results are rarely used. |
